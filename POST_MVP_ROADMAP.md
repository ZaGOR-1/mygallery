# Post-MVP Roadmap

Цей файл містить тільки майбутні задачі для розвитку фотогалереї. Уже реалізовані можливості перенесені в `IMPLEMENTED_FEATURES.md`.

Мета roadmap - нарощувати корисні можливості без Laravel, React, Bootstrap, Composer і зайвої архітектури. Проєкт має залишатися простим, зрозумілим і переносимим між WampServer та LAMP.

## Пріоритети

- `P1` - робити найближчим часом, дає найбільшу практичну користь.
- `P2` - корисно після стабілізації P1.
- `P3` - приємна фіча або UX-покращення, можна відкласти.
- `P4` - великий напрямок, робити тільки якщо справді з’явиться потреба.

## Поточний Висновок

Після пошуку й альбомів найцінніші наступні кроки:

1. Масове завантаження JPEG.
2. Сторінка технічного стану для адміністратора.
3. Backup/restore інструменти.
4. Download оригіналу тільки для адміністратора.
5. CLI-регенерація large/thumbnail.

Що варто переробити або уточнити перед новими великими фічами:

- Не поспішати з тегами. Альбоми вже закривають базову організацію.
- Backup варто підняти вище, бо фото - головна цінність проєкту.
- Admin health page варто зробити раніше за декоративні UX-фічі, бо проєкт планується переносити на Linux.
- Bulk upload краще почати зі звичайного `<input type="file" multiple>`, без drag-and-drop і AJAX.
- Для великих колекцій корисніший CLI-import із папки, ніж нескінченне розширення web-upload.

## P1: Масове Завантаження JPEG

Проблема: зараз фото завантажуються по одному. Для реальної фотогалереї це швидко стане незручно.

Що додати:

- `<input type="file" multiple>`;
- обробку кількох JPEG за один POST;
- окремий результат для кожного файла: завантажено або помилка;
- обмеження кількості файлів за раз, наприклад 10;
- показ короткого підсумку після upload.

Користь:

- швидше наповнення галереї;
- менше ручної роботи;
- зручніше після появи альбомів.

Ймовірні файли:

- `public/admin/upload.php`;
- `app/includes/functions.php`;
- `config/config.php`;
- `README.md`;
- `AGENTS.md`.

Ризики:

- великі POST-запити можуть упиратися в `post_max_size`;
- GD може з’їсти багато RAM при серійній обробці;
- треба акуратно чистити частково створені файли при помилках.

Рекомендація:

- не робити одразу drag-and-drop;
- не робити AJAX upload на першому кроці;
- обробляти файли послідовно, щоб не збільшувати RAM-сплески.

## P1: Admin Health / Status Page

Проблема: частина помилок залежить від середовища: PHP modules, права на папки, upload limits, database connection.

Що додати:

- сторінку `public/admin/health.php`;
- перевірку PHP версії;
- перевірку модулів `pdo_mysql`, `gd`, `exif`, `fileinfo`;
- перевірку прав запису в `storage/originals`, `storage/trash`, `storage/logs`, `storage/sessions`, `public/uploads/large`, `public/uploads/thumbnails`;
- показ поточних `upload_max_filesize`, `post_max_size`, `memory_limit`;
- перевірку підключення до БД;
- перевірку наявності таблиць `admins`, `albums`, `photos`, `login_attempts`;
- перевірку, що `APP_URL` відповідає очікуваному хосту;
- посилання на CLI-команду `tools/self_check.php`.

Користь:

- простіше переносити з WampServer на Linux;
- швидше діагностувати "чому не завантажується фото";
- легше перевірити сервер перед показом проєкту.

Ризики:

- сторінка тільки для адміністратора;
- не показувати пароль БД, абсолютні приватні шляхи або секрети;
- не показувати stack trace в production.

## P1: Backup І Restore

Проблема: фото і БД легко втратити, якщо переносити проєкт вручну або тестувати на VM.

Що додати:

- `tools/backup.php` або `tools/backup.ps1` для Windows;
- інструкцію restore у README;
- перевірку, що backup не містить `.git`, `config/database.php`, logs, sessions;
- архівацію `storage/originals`, `public/uploads/large`, `public/uploads/thumbnails`;
- експорт БД через `mysqldump`;
- приклад cron/systemd timer для Linux.

Користь:

- менше ризику втратити фото;
- простіше переносити на Proxmox/LAMP;
- зрозумілий сценарій відновлення після помилки.

Ризики:

- не зберігати backup у `public/`;
- не комітити backup у Git;
- не друкувати пароль БД у лог.

Рекомендація:

- почати з документації restore і простого Windows PowerShell backup;
- PHP backup робити тільки якщо він справді зручніший за CLI-інструменти.

## P2: Download Оригіналу Тільки Для Адміністратора

Поточний стан:

- оригінали лежать приватно в `storage/originals`;
- публічно показується optimized large version.

Що додати:

- кнопку "Завантажити оригінал" на сторінці фото тільки для admin;
- endpoint `public/admin/download.php?id=...`;
- перевірку доступу через `require_admin()`;
- віддачу файлу через `readfile()` з правильними headers.

Користь:

- адмін може забрати оригінальний JPEG без доступу до файлової системи;
- приватне сховище оригіналів стає реально зручним.

Ризики:

- не можна дозволяти path traversal;
- не можна віддавати файл без перевірки БД і `realpath`;
- не показувати приватні storage-шляхи.

## P2: CLI Import JPEG Із Папки

Проблема: для великої колекції web-upload незручний і залежить від `post_max_size`.

Що додати:

- `tools/import_photos.php`;
- параметр папки-джерела;
- dry-run режим;
- опціональний `--album="Назва альбому"`;
- пропуск уже імпортованих файлів за checksum або original_name + size;
- той самий pipeline перевірок, EXIF, large і thumbnail.

Користь:

- зручно імпортувати багато старих JPEG;
- менше залежності від browser upload;
- корисно перед переносом на Linux.

Ризики:

- треба не чіпати оригінальні файли у source-папці;
- треба логувати помилки по кожному файлу;
- треба уникати дублювання.

## P2: CLI Регенерація Зображень

Проблема: якщо змінити якість JPEG, `LARGE_MAX_WIDTH` або thumbnail width, старі файли залишаться у старому форматі.

Що додати:

- `tools/regenerate_images.php`;
- режими:
  - regenerate thumbnails;
  - regenerate large;
  - regenerate all;
- dry-run режим;
- логування помилок.

Користь:

- можна безпечно міняти налаштування зображень;
- простіше відновлювати `public/uploads` із приватних оригіналів.

Ризики:

- може довго працювати на великій галереї;
- може сильно навантажувати CPU/RAM;
- не можна перезаписувати оригінали.

## P2: Покращена Адмінка Для Керування Фото

Що додати:

- checkbox-вибір кількох фото;
- масове видалення через POST + CSRF;
- масова зміна альбому;
- фільтр "без опису", "без EXIF", "без дати зйомки", "без альбому";
- показ розміру оригіналу і large-версії;
- підтвердження з кількістю вибраних фото.

Користь:

- адмінка стане кориснішою при великій кількості фото;
- легше чистити й упорядковувати галерею після bulk upload.

Ризики:

- масові дії тільки через POST;
- треба уникати випадкового видалення великої кількості фото;
- бажано мати окремий endpoint `public/admin/bulk.php`.

## P2: Public Albums Page

Проблема: альбоми вже є, але публічно вони доступні тільки через select-фільтр.

Що додати:

- сторінку `/albums.php`;
- список альбомів із кількістю фото;
- обкладинку альбому за останнім або вручну вибраним фото;
- посилання на `gallery.php?album_id=...`;
- стан "альбомів поки немає".

Користь:

- альбоми стають видимою частиною сайту;
- користувачу легше перейти в потрібну тему без фільтр-форми.

Ризики:

- якщо додавати обкладинку вручну, потрібне поле `cover_photo_id`;
- для першої версії краще автоматична обкладинка.

## P2: Статистика

Що показувати:

- загальна кількість фото;
- кількість альбомів;
- кількість фото без альбому;
- сумарний розмір оригіналів;
- сумарний розмір large/thumbnails;
- найчастіша камера;
- кількість фото з EXIF і без EXIF;
- роки/місяці зйомки;
- найбільші файли.

Користь:

- цікаво для фотогалереї;
- допомагає бачити, що займає місце;
- корисно після backup/restore.

Ймовірні файли:

- `public/admin/stats.php`;
- `app/includes/functions.php`;
- `public/assets/css/style.css`.

## P2: Responsive Images / Medium Версії

Проблема: зараз є thumbnail і large. Для різних екранів можна зробити віддачу акуратнішою.

Що додати:

- `public/uploads/medium`, наприклад 1200 px;
- `srcset` для thumbnails/medium/large;
- `sizes` у gallery cards;
- CLI-регенерацію medium для старих фото.

Користь:

- швидше завантаження на мобільних;
- менше трафіку;
- кращий Lighthouse/PageSpeed.

Ризики:

- треба продумати міграцію для вже завантажених фото;
- WebP/AVIF не додавати без окремого рішення, бо поточний проєкт тримається на JPEG.

## P3: Архів За Роками І Місяцями

Що додати:

- сторінку `/archive.php`;
- групування фото за `taken_at`;
- fallback на `created_at`, якщо EXIF-дати немає;
- фільтр за альбомом у архіві.

Користь:

- природна навігація для фотогалереї;
- корисно без складних тегів.

Ризики:

- треба акуратно працювати з `NULL taken_at`;
- бажано використати існуючий індекс `taken_at`.

## P3: Покращення Лайтбокса

Що можна додати:

- подвійний клік: 100% <-> 200%;
- клавіші `ArrowLeft` / `ArrowRight` для переходу між фото;
- показ "1 з N";
- touch pinch zoom для телефона;
- preload попереднього/наступного фото.

Користь:

- перегляд стає ближчим до нормального photo viewer.

Ризики:

- JS може стати занадто великим для простого проєкту;
- touch/pinch треба тестувати на реальному телефоні.

## P3: Кращий UX Завантаження

Що додати:

- client-side preview перед upload;
- показ вибраного файла, розміру і MIME;
- попередження, якщо файл більший за поточний ліміт;
- після успішного upload вести одразу на сторінку фото або залишати в адмінці за налаштуванням.

Рекомендація:

- почати з preview і показу розміру файла;
- progress bar і AJAX upload не робити, поки немає реальної потреби.

## P3: Краща Робота З EXIF

Що додати:

- окрема кнопка "Показати всі EXIF";
- компактний режим і повний режим;
- нормальні людські назви для більшої кількості полів;
- показ GPS тільки якщо користувач явно цього хоче.

Важливо:

- GPS-координати можуть бути приватними даними;
- якщо додавати GPS, краще мати налаштування `SHOW_GPS_EXIF => false` за замовчуванням.

## P3: Changelog І Версія Застосунку

Що додати:

- `CHANGELOG.md`;
- `APP_VERSION` у `config/config.php`;
- показ версії у footer тільки для admin або у README;
- коротку секцію "Що змінилось" після великих фіч.

Користь:

- легше пояснювати розвиток проєкту;
- простіше робити локальні Git-коміти.

## P4: Теги

Коли може знадобитися:

- якщо одного альбому на фото стане замало;
- якщо треба багато перетинів, наприклад "природа", "ніч", "Nikon", "макро".

Що потрібно:

- таблиця `tags`;
- таблиця `photo_tags`;
- UI для додавання тегів;
- фільтр за тегом;
- сторінка тегів.

Рекомендація:

- не робити зараз;
- спочатку перевірити, чи альбоми справді не закривають потребу.

## P4: Публічні / Приватні Альбоми

Що додати:

- поле `is_public`;
- приховані альбоми;
- можливо пароль на альбом.

Ризики:

- це вже майже система доступів;
- треба дуже уважно тестувати, щоб приватні фото не витікали через прямі URL;
- optimized large files у `public/uploads` потребують окремої моделі доступу, якщо фото стають приватними.

Рекомендація:

- робити тільки якщо сайт буде відкритий в інтернеті і справді потрібна приватність на рівні окремих фото/альбомів.

## P4: RAW / NEF Workflow

AGENTS.md прямо каже не додавати RAW/NEF у MVP. Але як майбутній великий напрямок це можливо.

Що потрібно:

- зовнішній інструмент на сервері, наприклад `darktable-cli`, `dcraw` або ImageMagick з відповідними delegate;
- CLI-імпорт, не web-upload;
- окремі ліміти RAM/CPU;
- чітке розділення RAW-оригіналу і JPEG-прев’ю.

Рекомендація:

- не робити зараз;
- спочатку довести JPEG workflow, backup, restore і CLI-import.

## P4: API

Не рекомендується зараз.

Причина:

- MVP не потребує REST API;
- AGENTS.md прямо просить не додавати REST API в MVP;
- API одразу тягне authentication, rate limits, JSON contracts, versioning.

Коли може знадобитися:

- якщо буде окремий мобільний застосунок;
- якщо галерея стане частиною іншого сайту.

## Що Краще Не Додавати Найближчим Часом

Не варто додавати зараз:

- реєстрацію звичайних користувачів;
- коментарі;
- лайки;
- рейтинги;
- соціальні мережі;
- оплату;
- складну систему ролей;
- React/Vue;
- Laravel/Symfony;
- Composer-пакети без гострої потреби;
- RAW/NEF upload у веб-формі;
- хмарне сховище.

Причина:

- ці фічі різко збільшують складність;
- вони розмивають головну ідею персональної фотогалереї;
- для студентського MVP краще мати простий, зрозумілий і стабільний код.

## Рекомендований Порядок Реалізації

1. `P1` Масове завантаження JPEG.
2. `P1` Admin health/status page.
3. `P1` Backup/restore.
4. `P2` Download оригіналу тільки для адміністратора.
5. `P2` CLI import JPEG із папки.
6. `P2` CLI regenerate images.
7. `P2` Покращена адмінка для масових дій.
8. `P2` Public albums page.
9. `P2` Статистика.
10. `P3` Архів за роками/місяцями.
11. `P3` Покращення лайтбокса.
12. `P3` UX preview перед upload.

Якщо робити тільки три наступні задачі, найкращий набір:

1. Масове завантаження JPEG.
2. Admin health/status page.
3. Backup/restore.

Ці три задачі найкраще балансують зручність, надійність і підготовку до перенесення на Linux.
