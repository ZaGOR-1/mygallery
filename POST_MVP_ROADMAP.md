# Post-MVP Roadmap

Цей файл містить ідеї для розвитку фотогалереї після MVP. Поточний MVP уже має базову галерею, адмінку, JPEG-upload, EXIF, прев'ю, large-версії фото, приватні оригінали, безпеку форм, brute-force захист, cleanup tools і лайтбокс із zoom/pan.

Мета наступних покращень - не перетворити студентський PHP-проєкт на складний фреймворк, а акуратно нарощувати корисні можливості без Laravel, React, Bootstrap, Composer і зайвої архітектури.

## Пріоритети

- `P1` - варто зробити першим, дає найбільшу користь або прибирає майбутній біль.
- `P2` - корисне покращення після стабілізації.
- `P3` - приємна фіча, можна відкласти.
- `P4` - велике розширення, робити тільки якщо справді потрібно.

## P1: Пошук і фільтри в галереї

Статус: реалізовано.

Проблема: коли фотографій стане багато, пагінації буде недостатньо. Зараз можна тільки гортати сторінки.

Що додати:
- пошук за назвою;
- пошук за описом;
- фільтр за камерою;
- фільтр за датою зйомки;
- сортування: новіші, старіші, дата зйомки, назва.

Користь:
- галерея стане зручною після 100+ фотографій;
- адмінці буде легше знаходити конкретне фото.

Ймовірні файли:
- `public/gallery.php`;
- `public/admin/index.php`;
- `database/schema.sql`;
- `public/assets/css/style.css`.

База:
- індекс `title` уже є;
- можна додати індекс на `description(191)` тільки якщо пошук по опису стане повільним;
- для складного пошуку можна розглянути `FULLTEXT`, але для MVP+ краще почати з простого `LIKE`.

Ризики:
- треба уважно будувати SQL тільки через prepared statements;
- треба зберігати параметри фільтрів у пагінації.

## P1: Теги або альбоми

Проблема: зараз усі фото лежать в одному потоці. З часом буде важко розділяти "природа", "місто", "сім'я", "техніка", "Nikon D7100" тощо.

Варіант A - альбоми:
- одна фотографія належить одному альбому;
- простіше реалізувати;
- достатньо таблиці `albums` і поля `album_id` у `photos`.

Варіант B - теги:
- одна фотографія може мати багато тегів;
- гнучкіше;
- потрібні таблиці `tags` і `photo_tags`.

Рекомендація:
- для цього проєкту краще почати з альбомів;
- теги додавати тільки якщо альбомів стане замало.

Ймовірні файли:
- `database/schema.sql`;
- `public/gallery.php`;
- `public/photo.php`;
- `public/admin/upload.php`;
- `public/admin/edit.php`;
- `public/admin/index.php`.

Ризики:
- треба продумати поведінку при видаленні альбому;
- треба оновити README і схему БД.

## P1: Масове завантаження JPEG

Проблема: зараз фото завантажуються по одному. Для реальної фотогалереї це швидко стане незручно.

Що додати:
- `<input type="file" multiple>`;
- обробку кількох JPEG за один POST;
- окремий результат для кожного файлу: завантажено або помилка;
- обмеження кількості файлів за раз, наприклад 10.

Користь:
- можна швидше наповнювати галерею;
- менше ручної роботи.

Ймовірні файли:
- `public/admin/upload.php`;
- `app/includes/functions.php`;
- `config/config.php`;
- `README.md`.

Ризики:
- великі POST-запити можуть упиратися в `post_max_size`;
- GD може з'їсти багато RAM при серійній обробці;
- треба акуратно чистити частково створені файли при помилках.

Рекомендація:
- не робити одразу drag-and-drop;
- спочатку зробити просте multiple upload через стандартний HTML input.

## P1: Сторінка технічного стану для адміністратора

Проблема: частина помилок залежить від середовища: PHP modules, права на папки, upload limits, database connection.

Що додати:
- сторінку `public/admin/health.php`;
- перевірку PHP версії;
- перевірку модулів `pdo_mysql`, `gd`, `exif`, `fileinfo`;
- перевірку прав запису в `storage/originals`, `storage/trash`, `storage/logs`, `public/uploads/large`, `public/uploads/thumbnails`;
- показ поточних `upload_max_filesize`, `post_max_size`, `memory_limit`;
- перевірку підключення до БД;
- кнопку/посилання на запуск інструкції `tools/self_check.php` з консолі.

Користь:
- простіше переносити з WampServer на Linux;
- швидше діагностувати "чому не завантажується фото".

Ймовірні файли:
- `public/admin/health.php`;
- `app/includes/functions.php`;
- `app/includes/header.php`;
- `README.md`.

Ризики:
- не показувати секрети з `config/database.php`;
- не показувати абсолютні системні шляхи звичайним відвідувачам;
- сторінка тільки для адміністратора.

## P2: Покращена адмінка для керування фото

Що додати:
- checkbox-вибір кількох фото;
- масове видалення через POST + CSRF;
- швидке редагування назви прямо у списку;
- фільтр "без опису", "без EXIF", "без дати зйомки";
- показ розміру оригіналу і large-версії.

Користь:
- адмінка стане корисною при великій кількості фото;
- легше чистити й упорядковувати галерею.

Ймовірні файли:
- `public/admin/index.php`;
- `public/admin/edit.php`;
- `public/admin/delete.php`;
- можливо `public/admin/bulk.php`;
- `public/assets/css/style.css`;
- `public/assets/js/main.js`.

Ризики:
- масові дії мають бути тільки POST;
- треба уникати випадкового видалення великої кількості фото;
- краще додати підтвердження з кількістю вибраних фото.

## P2: Download оригіналу тільки для адміністратора

Поточний стан:
- оригінали лежать приватно в `storage/originals`;
- публічно показується optimized large version.

Що додати:
- кнопку "Завантажити оригінал" на сторінці фото тільки для admin;
- endpoint `public/admin/download.php?id=...`;
- перевірку доступу через `require_admin()`;
- віддачу файлу через `readfile()` з правильними headers.

Користь:
- можна зберігати якісний архів;
- адмін може забрати оригінальний JPEG без доступу до файлової системи.

Ризики:
- не можна дозволяти path traversal;
- не можна віддавати файл без перевірки БД і `realpath`;
- не показувати приватні storage-шляхи.

## P2: Кращі прев'ю і responsive images

Проблема: зараз є thumbnail і large. Для різних екранів можна зробити віддачу ще акуратнішою.

Що додати:
- `public/uploads/medium`, наприклад 1200 px;
- `srcset` для thumbnails/medium/large;
- `sizes` у gallery cards;
- WebP/AVIF не додавати без окремого рішення, бо AGENTS.md орієнтує першу версію на JPEG.

Користь:
- швидше завантаження на мобільних;
- менше трафіку;
- кращий Lighthouse/PageSpeed.

Ймовірні файли:
- `app/includes/functions.php`;
- `public/admin/upload.php`;
- `public/gallery.php`;
- `public/index.php`;
- `public/photo.php`;
- `database/schema.sql`, якщо medium матиме окреме ім'я.

Ризики:
- треба продумати міграцію для вже завантажених фото;
- потрібен CLI-скрипт для генерації medium для старих фото.

## P2: CLI-інструмент для регенерації прев'ю

Проблема: якщо змінити якість JPEG, `LARGE_MAX_WIDTH` або thumbnail width, старі файли залишаться у старому форматі.

Що додати:
- `tools/regenerate_images.php`;
- режими:
  - regenerate thumbnails;
  - regenerate large;
  - regenerate all;
- dry-run режим;
- логування помилок.

Користь:
- можна безпечно міняти налаштування зображень;
- простіше відновлювати `public/uploads` із приватних оригіналів.

Ризики:
- може довго працювати на великій галереї;
- може сильно навантажувати CPU/RAM;
- треба не перезаписувати оригінали.

## P2: Backup і restore інструкції плюс CLI-скрипт

README уже описує резервне копіювання, але можна зробити зручніше.

Що додати:
- `tools/backup.php` або `tools/backup.ps1` для Windows;
- перевірку, що backup не містить `.git`, logs і secrets;
- окрему інструкцію restore;
- шаблон cron/systemd timer для Linux.

Користь:
- легше переносити на Proxmox/LAMP;
- менше ризику втратити фото.

Ризики:
- не зберігати backup у публічній папці;
- не комітити backup у Git;
- не друкувати пароль БД у лог.

## P2: Сторінка статистики

Що показувати:
- загальна кількість фото;
- сумарний розмір оригіналів;
- сумарний розмір large/thumbnails;
- найчастіша камера;
- кількість фото з EXIF і без EXIF;
- роки/місяці зйомки;
- найбільші файли.

Користь:
- цікаво для фотогалереї;
- допомагає бачити, що займає місце.

Ймовірні файли:
- `public/admin/stats.php`;
- `app/includes/functions.php`;
- `public/assets/css/style.css`.

## P3: Архів за роками і місяцями

Що додати:
- сторінку `/archive.php`;
- групування фото за `taken_at`;
- fallback на `created_at`, якщо EXIF-дати немає.

Користь:
- природна навігація для фотогалереї;
- корисно без складних тегів.

Ризики:
- треба акуратно працювати з `NULL taken_at`;
- бажано додати індекс, якщо запити стануть важкими.

## P3: Покращення лайтбокса

Поточний стан:
- відкриття на сторінці фото;
- кнопки zoom;
- wheel zoom;
- drag/pan.

Що можна додати:
- подвійний клік: 100% <-> 200%;
- клавіші `ArrowLeft` / `ArrowRight` для переходу між фото;
- показ "1 з N";
- touch pinch zoom для телефона;
- preload попереднього/наступного фото.

Користь:
- перегляд стає ближчим до нормального photo viewer.

Ризики:
- JS може стати занадто великим для простого проєкту;
- touch/pinch треба тестувати на реальному телефоні.

## P3: Кращий UX завантаження

Що додати:
- client-side preview перед upload;
- показ вибраного файлу, розміру і MIME;
- попередження, якщо файл більший за поточний ліміт;
- progress bar, якщо залишаємо звичайний POST - складніше, якщо без AJAX;
- після успішного upload вести одразу на сторінку фото або залишити в адмінці за налаштуванням.

Рекомендація:
- почати з preview і показу розміру файлу;
- не робити AJAX upload, поки немає реальної потреби.

## P3: Краща робота з EXIF

Що додати:
- окрема кнопка "Показати всі EXIF";
- компактний режим і повний режим;
- нормальні людські назви для більшої кількості полів;
- показ GPS тільки якщо користувач явно цього хоче.

Важливо:
- GPS-координати можуть бути приватними даними;
- якщо додавати GPS, краще мати налаштування `SHOW_GPS_EXIF => false` за замовчуванням.

## P3: Налаштування через admin UI

Що можна налаштовувати:
- назва сайту;
- кількість фото на сторінку;
- показ/приховування EXIF;
- якість large JPEG;
- ширина large JPEG;
- ширина thumbnail.

Рекомендація:
- не поспішати з цим;
- для простого студентського проєкту `config/config.php` поки достатньо;
- admin settings потребують нової таблиці й додаткової валідації.

## P4: RAW/NEF workflow

AGENTS.md прямо каже не додавати RAW/NEF у MVP. Але як майбутній великий напрямок це можливо.

Що потрібно:
- зовнішній інструмент на сервері, наприклад `darktable-cli`, `dcraw` або `ImageMagick` з відповідними delegate;
- черга обробки або CLI-імпорт;
- окремі ліміти RAM/CPU;
- чітке розділення RAW-оригіналу і JPEG-прев'ю.

Рекомендація:
- не робити зараз;
- спочатку довести JPEG workflow, backup і альбоми.

## P4: Публічні/приватні альбоми

Що додати:
- поле `is_public`;
- приховані альбоми;
- можливо пароль на альбом.

Ризики:
- це вже майже система доступів;
- треба дуже уважно тестувати, щоб приватні фото не витікали через прямі URL.

Рекомендація:
- робити тільки якщо сайт буде відкритий в інтернеті і справді потрібна приватність на рівні окремих фото/альбомів.

## P4: API

Не рекомендується зараз.

Причина:
- MVP не потребує REST API;
- AGENTS.md прямо просить не додавати REST API в MVP;
- API одразу тягне authentication, rate limits, JSON contracts, versioning.

Коли може знадобитися:
- якщо буде окремий мобільний застосунок;
- якщо галерея стане частиною іншого сайту.

## Технічні покращення без нових фіч

Це не помітно користувачу, але покращує якість проєкту.

1. Додати простий `tools/self_check.php --full`
   - перевірка БД;
   - перевірка schema.sql;
   - перевірка upload/storage;
   - перевірка orphan-файлів;
   - перевірка security headers через локальний URL.

2. Додати мінімальні fixture-дані для локального тесту
   - не приватні фото;
   - маленькі JPEG;
   - різні EXIF-випадки.

3. Додати ручний checklist перед релізом
   - upload;
   - edit;
   - delete;
   - login/logout;
   - gallery pagination;
   - photo navigation;
   - lightbox zoom/pan/wheel;
   - Linux path case check.

4. Додати версію застосунку
   - `APP_VERSION`;
   - показ у footer тільки для admin або у README.

5. Додати changelog
   - `CHANGELOG.md`;
   - коротко фіксувати важливі зміни.

## Що краще не додавати зараз

Не варто додавати найближчим часом:
- реєстрацію звичайних користувачів;
- коментарі;
- лайки;
- рейтинги;
- соціальні мережі;
- оплату;
- складну систему ролей;
- React/Vue;
- Laravel/Symfony;
- Composer-пакети без гострої потреби;
- RAW/NEF upload у веб-формі;
- хмарне сховище.

Причина:
- ці фічі різко збільшують складність;
- вони розмивають головну ідею персональної фотогалереї;
- для студентського MVP краще мати простий, зрозумілий і стабільний код.

## Рекомендований порядок реалізації

1. `P1` Пошук і фільтри.
2. `P1` Альбоми.
3. `P1` Масове завантаження JPEG.
4. `P1` Admin health/status page.
5. `P2` Download оригіналу тільки для адміністратора.
6. `P2` CLI regenerate images.
7. `P2` Статистика.
8. `P3` Архів за роками/місяцями.
9. `P3` Покращення лайтбокса.
10. `P3` UX preview перед upload.

Якщо робити тільки три наступні задачі, найкращий набір:

1. Пошук і фільтри.
2. Альбоми.
3. Масове завантаження JPEG.

Ці три покращення найсильніше перетворять MVP із "працює" на "зручно користуватися".
