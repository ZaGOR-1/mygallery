## 🔴 CRITICAL

### C1. Захист входу від брутфорсу обходиться тривіальною арифметичною CAPTCHA — ✅ ВИПРАВЛЕНО (v6.4.7)
**Файл:** `public/admin/login.php:200-217`

> **Статус:** виправлено. CAPTCHA-механізм прибрано; локаут тепер суто час-базований (`locked_until`): поки bucket залоковано, спроба входу відхиляється з заголовком `Retry-After`, і ніщо не обнуляє лок. Перевірено: `php -l` ✅, `php tests/run.php` → 9/9 ✅.

Коли bucket залоковано (`$lockSecondsLeft > 0`), єдиний наслідок — математична CAPTCHA виду `num1 + num2`, де **обидва доданки показані користувачу** (`login_captcha_question`, рядок 212/276). При правильній відповіді код робить `$lockSecondsLeft = 0` (рядок 216) і вхід продовжується штатно. Простір відповідей — суми 2–20, а сам приклад відкрито в HTML, тож автоматизований атакер розвʼязує його кожного разу і **продовжує необмежений підбір пароля**. Часового локауту, який реально відмовляв би у спробі, немає.

Це підриває вимогу `AGENTS.md` «обмежуй невдалі спроби входу через `login_attempts`».

**Фікс:** коли `login_lock_seconds_for() > 0`, **жорстко відхиляти** спробу входу з генеричною помилкою незалежно від CAPTCHA (повертати «Забагато спроб, зачекайте N сек.»), або замінити арифметику на справжню непередбачувану CAPTCHA І зберегти часовий тротлінг. Розвʼязана CAPTCHA не повинна обнуляти часовий лок.

## 🟠 HIGH

### H1. Завантаження альбому ZIP віддає приватні byte-for-byte оригінали анонімним користувачам — ✅ ВИПРАВЛЕНО (v6.4.8)
**Файл:** `public/download_album.php:208-212` (+ token-гілка `94-122`)

> **Статус:** виправлено. Прийнято політику «оригінали тільки для адміна»: byte-for-byte оригінали зі `storage/originals` тепер беруться лише при `is_admin_logged_in()`; публічні (`?album_id=`) та share-токен завантаження отримують виключно оптимізовану `uploads/large`. Варіант (`orig`/`opt`) додано в ключ кешу, тож адмінський ZIP з оригіналами не віддається не-адміну з кешу. Перевірено: `php -l` ✅, `php tests/run.php` → 9/9 ✅.

У циклі формування ZIP першим джерелом є `storage/originals` (рядок 209), і лише як fallback — `uploads/large`. Тобто **публічне** завантаження альбому (`?album_id=`) або завантаження за share-токеном віддає повнорозмірні приватні оригінали. Це суперечить правилу `AGENTS.md` «download original тільки для адміна» та «приватні byte-for-byte оригінали в `storage/originals`».

Додатково: token-гілка (рядки 94-122) не перевіряє `albums.is_private` (на відміну від `album_id`-гілки на рядку 139). Для share-лінка це прийнятно (лінк свідомо надає доступ), але оригінали все одно не мають витікати.

**Фікс:** ухвалити явну політику. Якщо ZIP-завантаження для не-адмінів має містити лише оптимізовані версії — для не-адмінських/токен-завантажень брати тільки `uploads/large`, а `storage/originals` лишити виключно за `is_admin_logged_in()`. Якщо оригінали в публічному ZIP справді задумані — задокументувати це і прибрати з правил «originals only for admin».

### M3. Відновлення БД та міграції не транзакційні — частковий збій лишає неконсистентний стан — ✅ ВИПРАВЛЕНО (v6.4.11)
**Файли:** `tools/restore.php:275-285`, `tools/migrate.php:33-39`

`restore.php` виконує дамп `DELETE`+`INSERT` одним `exec()` без транзакції/safety-backup; збій посередині лишає БД напіввідновленою, а медіа от-от буде стерто. `migrate.php` виконує кожен файл одним `exec()`; DDL у MySQL автокомітиться, тож при частковому збої міграція не записується і повторний запуск падає.
**Фікс:** робити safety-backup перед restore (або прибирати `LOCK TABLES` з дампу і обгортати застосування в транзакцію); вимагати/документувати ідемпотентність кожної міграції (`IF NOT EXISTS`/`IF EXISTS`).
*(Зайвий мертвий код: `restore.php:268-273,285` пише `$tmpSql`, який ніде не використовується.)*

> **Статус:** виправлено. `restore.php` застосовує дамп у транзакції (`beginTransaction`/`commit`/`rollBack`) — частковий збій повністю відкочується, а медіа стираються лише після успіху. `backup.php` більше не генерує `LOCK TABLES`/`UNLOCK TABLES` (вони роблять неявний COMMIT і ламали б транзакцію); старі бекапи з ними застосовуються по-старому (неатомарно) з попередженням. Мертвий код `$tmpSql` прибрано. `migrate.php` явно обробляє помилку кожної міграції й документує контракт ідемпотентності (DDL автокомітиться, тож half-applied міграція просто не записується і повторний запуск догоняє стан); наявні міграції вже захищені `IF NOT EXISTS`/`information_schema`-перевірками. Перевірено: `php -l` (restore/backup/migrate) ✅.

## ℹ️ Підтверджено як коректне (без дій)

- **Upload-валідація**: JPEG примусово через `finfo_file` **і** `getimagesize`; розширення не довіряється; імʼя рандомізоване; оригінал у `storage/originals`; ліміти розміру/габаритів/пікселів перевіряються до GD.
- **GD на основному resize-шляху**: результати `imagecreatetruecolor/imagecopyresampled/imagerotate/imageflip/imagejpeg` перевіряються, є `imagedestroy`.
- **EXIF Orientation 1–8**: оброблено коректно, включно зі свопом W/H для 5/6/7/8.
- **Path traversal**: `valid_photo_filename` (`^[a-f0-9]{32}\.(jpg|webp|avif)$`) + `realpath` + `str_starts_with(base)` усюди; restore валідує ZIP-entries до мутацій; tools мають CLI-only guard.
- **SQL**: усе на PDO prepared statements; `ORDER BY` whitelisted; `LIMIT/OFFSET` біндяться `PARAM_INT`.
- **CSRF / require_admin**: усі адмін-сторінки під `require_admin()`; усі state-changing POST під `require_csrf()`; логін/логаут — POST+CSRF; `session_regenerate_id(true)` після входу; dummy-hash проти user enumeration; генерична помилка входу.
- **Приватність у public**: `photo.php`/`gallery.php`/`albums.php` коректно ховають приватні альбоми від не-адмінів (з застереженням M6).
- **Debug-витоки**: `display_errors`/stack trace під `APP_DEBUG`; production hard-fail при debug=on; SQL-помилки не показуються.
- **Реліз-гігієна**: `build_release.php` виключає `.git/.env/config/database.php`/медіа/логи/сесії/backups/dist/`temp_*`/`*.bak/*.tmp/*.zip` (подвійний захист).
- **Без command injection**: жодного `exec/shell_exec/system/proc_open/passthru`.
